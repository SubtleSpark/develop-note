# 聚合广告平台

## 一、项目背景

**业务背景**：公司拥有多个高流量入口，希望通过广告实现流量变现。

**架构演进**：

| 阶段 | 方案 | 问题 |
|------|------|------|
| V1 | 纯客户端：App 直连各 ADN，本地比价 | 每次新增 ADN 需发版，强耦合 |
| V2 | 聚合平台：服务端多路召回+竞价 | - |

**V2 方案优势**：
1. **客户端轻量化**：不再关心请求了几个 ADN，逻辑大幅简化
2. **灵活迭代**：新接入 ADN 只需升级服务端，App 无需发版
3. **功能扩展**：支持 AB 实验组区分、频控等精细化流量控制

**核心指标**：
- 峰值 QPS：7000
- P99 延迟：TODO

## 四、核心功能模块

### 4.1 广告配置下发

- **功能描述**：下发投放策略、AB 实验配置、频控规则等
- **技术实现**：三级缓存架构

```
┌─────────────┐    ┌─────────────┐    ┌─────────────┐
│  机器内存    │ ←  │    Redis    │ ←  │    MySQL    │
│  (L1 缓存)   │    │  (L2 缓存)   │    │  (持久化)    │
└─────────────┘    └─────────────┘    └─────────────┘
      ↑ 定时 30s 拉取
```

| 操作 | 策略 |
|------|------|
| 写入 | Redis + MySQL 双写 |
| 读取 | 每个 Pod 定时 30s 从 Redis 同步到机器内存 |
| 优势 | 纯内存读取，保证广告请求的极致性能 |

### 4.2 广告多路召回

- **功能描述**：并发请求多个 ADN，合并结果进行竞价
- **技术实现**：
  - 并发模型：goroutine 并发请求各 ADN
  - 容错策略：单个 ADN 超时/失败直接忽略，所有 ADN 互为兜底
  - 结果合并：汇总所有 ADN 返回的广告，按 eCPM 排序竞价

### 4.3 素材审核

- **功能描述**：广告素材的合规性审核
- **技术实现**：adxserver 调用 adxcheck 的 upsertMeta，将素材插入 MQ，异步审核
- **难点/亮点**：TODO（重构了底层存储，待补充细节）

### 4.4 频控系统

- **功能描述**：
  - 日曝光量频控：一个实验组一天限制 N 次（如 5000 次）
  - 曝光频率频控：一个实验组每 5 分钟限制 N 次（如 500 次）

- **技术实现**：

| 类型 | 实现方案 | Redis Key 示例 |
|------|----------|----------------|
| 日曝光量 | 每天一个 key，INCR 原子累加 | `exp:{gid}:2024-01-26` |
| 曝光频率 | 5 秒粒度滑动窗口，每 5 秒一个 key | `exp:{gid}:{ts/5}` |

- **曝光频率实现细节**：
  - 每 5 秒记录一个 Redis key，存储这 5 秒内的曝光量
  - 请求时计算过去 5 分钟（60 个桶）的曝光总量
  - 使用 INCR 原子操作保证并发安全

## 五、性能优化

### 5.1 Waterfall/Bidding 混合竞价优化（提升 eCPM）

**广告竞价模式说明**：

| 模式 | 机制 | 特点 |
|------|------|------|
| Waterfall | 按优先级逐一询价，「排队制」 | 串行，耗时长，但价格稳定 |
| Bidding | 所有买家同时出价，「拍卖制」 | 并行，速度快（约 400ms） |

**优化前的问题**：
- 原有 adreq 混合返回 Waterfall 和 Bidding 广告
- 客户端按顺序请求，如果前几个是 Waterfall，用户感知广告加载很慢
- Waterfall 请求数量受限于等待时间，eCPM 无法最大化

**优化方案**：
```
┌──────────────────────────────────────────────────────────┐
│ 客户端                                                    │
├──────────────────────────────────────────────────────────┤
│  1. 获取 Waterfall 广告位列表                              │
│  2. 开始串行请求 Waterfall 广告  ──┐                       │
│  3. 同时并行发送 Bid 请求 ────────────→ 服务端竞价(~400ms)  │
│  4. Bid 返回后，Waterfall 停止 ←──┘                       │
│  5. 比较 Waterfall 最高价 vs Bid 最高价，展示胜出者          │
└──────────────────────────────────────────────────────────┘
```

**核心效果**：
- 在相同等待时间内，Waterfall 可请求更多广告位，**提高 eCPM**
- 用户感知的广告加载时间不再受 Waterfall 数量影响

### 5.2 AC 自动机优化敏感词匹配

| 维度 | 内容 |
|------|------|
| **场景** | 广告素材的敏感词/关键词/URL 匹配，约 100+ 模式串 |
| **问题** | 原有 `strings.Contains` 逐个匹配，时间复杂度 O(n×m×k)，CPU 占用高 |
| **方案** | 引入 AC 自动机，一次扫描匹配所有模式串，时间复杂度 O(n+m) |
| **效果** | CPU 使用率降低 30%~40% |

**面试追问准备**：
- 为什么不用 Trie？Trie 需要对每个位置都从头匹配，AC 自动机通过 fail 指针避免回溯
- n=文本长度，m=模式串总长度，k=模式串数量

### 5.3 广告接入 SOP 优化

| 维度 | 内容 |
|------|------|
| **问题** | 新 ADN 接入流程不标准，每次接入耗时长 |
| **方案** | 抽象为 2 种 SKILL：标准 API（对方开发对接我们）、独立 API |
| **效果** | 标准 API 接入：1d → 0.25d；独立 API 接入：2d → 1d |

## 六、故障排查经验

### RocketMQ 消费不均问题

**现象**：
- 部分 Pod CPU 60% 持续告警
- 自动扩容未触发（基于 avg_cpu）
- MQ 积压监控正常

**排查过程**：
1. 发现只有一半 Pod 在消费消息，另一半 CPU ≈ 0
2. avg_cpu 被低负载 Pod 拉低，未触发扩容阈值
3. 联系基础架构排查

**根因**：基础架构侧 MQ 迁移，消息只路由到部分 partition

**解决**：协调架构侧调整 partition 分配

**反思**：
- avg_cpu 扩容策略在负载不均场景下失效
- 可考虑补充 max_cpu 或 CPU 方差监控

## 九、简历版本（可直接使用）

### 聚合广告平台

**项目背景**：

公司拥有多个高流量入口，原有纯客户端广告方案（App 直连各 ADN 本地比价）存在强耦合问题，每次新增广告网络需 App 发版。负责设计并实现服务端聚合广告平台，将多路召回和竞价逻辑上移至服务端，支撑峰值 7000 QPS 的广告请求。

**技术栈**：Golang / Gin / MySQL / TiDB / Redis / RocketMQ

**核心工作**：

- **Waterfall/Bidding 混合竞价优化**：原有接口混合返回两种广告，Waterfall 串行请求导致加载慢且请求量受限。拆分为独立接口后，客户端可并行请求 Bidding（~400ms）的同时串行请求 Waterfall，相同时间内提升广告请求量，提高 eCPM。
- **三级缓存架构**：设计机器内存→Redis→MySQL 的三级缓存，写入时 Redis+MySQL 双写，每个 Pod 定时 30s 同步配置到内存，实现纯内存读取，保障广告请求的极致性能。
- **分布式频控系统**：支持日曝光量（每天一个 Redis Key + INCR）和曝光频率（5 秒粒度滑动窗口）两种维度，使用原子操作保证 7000 QPS 下的高并发准确性。
- **敏感词匹配优化**：将 `strings.Contains` 逐个匹配（O(n×m×k)）优化为 AC 自动机一次扫描（O(n+m)），CPU 使用率降低 30%~40%。
- **广告接入 SOP 优化**：抽象标准 API 和独立 API 两种接入模式，接入效率提升 50%~75%。

**突出点**：

- **业务驱动的架构优化**：Waterfall/Bidding 拆分不是单纯的性能优化，而是基于广告变现策略的架构调整，体现对业务的深入理解
- **极致性能设计**：三级缓存 + 纯内存读取 + goroutine 并发召回，支撑高并发广告场景
- **算法工程化落地**：AC 自动机在实际业务中的应用，CPU 降低 30%~40%
